## 一、系统拓扑

```
 ┌──────────────┐   ESP-NOW     ┌────────────────┐   UART      ┌──────────────┐   CAN      ┌───────────┐
 │  ESP32 主机   │  2.4G 广播     │  M5Stamp S3    │  921600     │ STM32F103C8T6│  1 Mbps    │ DM-G6220  │
 │ 自主轨迹发生器 │ ────────────► │  桥接/看门狗    │ ──────────► │  MIT 闭环    │ ─────────► │ 云台电机   │
 │  (USB 调参)   │   50 Hz       │  (USB 调试口)   │   50 Hz     │   1 kHz     │            │  ID = 1   │
 └──────────────┘               └────────────────┘             └──────────────┘            └───────────┘
        ▲                                                              │
        └──────────────── 反馈帧（角度/温度/错误码）50 Hz ◄──────────────┘
```

数据流一句话：**主机算好目标角度 → ESP-NOW → 桥接转发 → STM32 转成 MIT 控制帧 → CAN → 电机**。

## 二、接线表

### 2.1 ESP-NOW 无线链路

三颗 ESP32 **不需要任何连线**，但必须满足：

| 项目 | 要求 |
|---|---|
| 信道 | 全部为 **6**（`esp32_master/include/app_config.h` 与 `esp32_bridge/include/app_config.h` 的 `ESPNOW_CHANNEL` 必须一致） |
| 距离 | 空旷环境几十米没问题；穿墙会衰减 |
| 天线 | M5Stamp 的 IPEX 天线**必须接上**，否则通信距离只有几厘米 |

### 2.2 桥接端 ↔ STM32（交叉串口）

| M5Stamp S3 | 方向 | STM32F103C8T6 | 说明 |
|---|---|---|---|
| **G1**（排针第 2 脚） | → | **PA10**（USART1_RX） | 桥接 TX 接 STM32 RX |
| **G2**（排针第 4 脚） | ← | **PA9**（USART1_TX） | 桥接 RX 接 STM32 TX |
| **GND** | ─ | **GND** | ★ **必须共地**，否则串口乱码/收不到 |
| 3V3 | | | 各自独立供电即可，**不要**用两路 USB 同时给同一块板供电 |

> **为什么不用 M5Stamp 的默认串口脚 G43/G44？**
> 官方手册「管脚映射」里写着：`G43 = U0TX`、`G44 = U0RX`，但 **G44 同时被板载 M5PM1 电源管理芯片当 SCL 用**（`M5PM1(0x6E) SCL SDA`），
> 而且 G13/G15 是板载 I2C。用这几根脚会和电源管理抢线，所以本方案改用排针上干净的 G1/G2。

### 2.3 STM32 ↔ SN65HVD230 ↔ 电机

| STM32F103C8T6 | 方向 | SN65HVD230 模块 | 说明 |
|---|---|---|---|
| **PB9** | → | **CTX**（TX） | CAN1_TX，**已重映射**（见下方 ★★） |
| **PB8** | ← | **CRX**（RX） | CAN1_RX，**已重映射** |
| **3V3** | → | **VCC** | ★ SN65HVD230 是 **3.3V** 器件，**不要接 5V** |
| **GND** | ─ | **GND** | 必须共地 |
| | | **CANH** | → 电机 CANH |
| | | **CANL** | → 电机 CANL |

> **★★ 重要：CAN 不是 PA11/PA12，是 PB8/PB9**
>
> 野火这块「双 USB 款」核心板把 **PA11/PA12 直接焊到了 USB TYPE-C 插座**上
> （规格书 2.4.7 节：USB_DM = PA11，USB_DP = PA12）。
> 而 PA11/PA12 恰好是 CAN1 的**默认**引脚 —— 板上这两个脚已被 USB 占死，
> 接 CAN 收发器**驱动不了**。
>
> 所以本工程在 `can_drv.c` 里把 `AFIO_MAPR` 的 `CAN_REMAP` 设成 `10`，
> 把 CAN1 **重映射到 PB8(CRX) / PB9(CTX)**，这两根脚在排针上是引出的。
>
> **接 PA11/PA12 = CAN 永远不通，现象是"电机完全没反馈"。**

**终端电阻（最容易忘、也最容易导致"完全没反馈"）**

- CAN 总线是差分总线，**两端各需要一个 120Ω 终端电阻**。
- SN65HVD230 模块上通常**没有**板载 120Ω。请确认：
  - 电机端一般已内置或需要外接；
  - 总线另一头（STM32/模块侧）要有一个 120Ω，接在 CANH 与 CANL 之间。
- 只有一端有电阻时，短距离低速可能勉强能跑；1 Mbps 下大概率直接不通。

### 2.3b OLED 状态屏（两块屏，各挂各的）

**第一块 → 野火 STM32F103C8T6（I2C1 默认脚）**

| OLED 引脚 | 接到 | 说明 |
|---|---|---|
| GND | GND | |
| VCC | **3V3** | ★ 只能 3.3V，接 5V 会烧屏 |
| SCL | **PB6** | I2C1_SCL |
| SDA | **PB7** | I2C1_SDA |

**第二块 → M5Stamp-S3Bat DIP**

| OLED 引脚 | 接到 | 说明 |
|---|---|---|
| GND | GND | |
| VCC | **3V3** | |
| SCL | **G9 / GPIO9** | |
| SDA | **G8 / GPIO8** | |

> **两块屏各自独立，不挂在同一条总线上。**
> 两块板是电气隔离的（只共地、各自供电），分开挂即使 I2C 地址都是 0x3C 也没关系。
> **不要**把两块板的 3V3 连在一起。

**为什么用软件 I2C：**
屏幕每秒只刷 10 次，软件 I2C 的 ~250kHz 完全够；不占用硬件 I2C 外设，
也避开了 F103 硬件 I2C 的著名勘误（总线锁死）。同一份 `oled.c` 通过函数指针就能跑在两颗芯片上。

**驱动芯片：** 默认按 **SSD1306** 初始化，代码会自动试 I2C 地址 `0x3C` 再试 `0x3D`。
如果是 **SH1106**，需要把 `display_*.c` 里的 `OLED_CTRL_SSD1306` 改成 `OLED_CTRL_SH1106`（会有 2 列偏移修正）。

**没接屏幕会怎样：** `display_init()` 返回 false，后续刷新自动跳过 —— **不影响电机控制**，也不影响串口链路。

### 2.4 供电

| 部件 | 供电 | 备注 |
|---|---|---|
| ESP32 主机 | USB（电脑） | 同时用作调参串口 |
| M5Stamp S3 | USB-C 或 3.7V 锂电池 | USB 口同时是调试串口 |
| STM32F103C8T6 | USB 或 5V | 野火核心板双 USB |
| SN65HVD230 | 3V3（取自 STM32 板） | 只给收发器，不驱动电机 |
| DM-G6220 | **独立电源** | ★ 电机是大电流负载，**必须独立供电**，不能从 STM32 的 3V3 取电 |

**共地要点**：STM32 的 GND、SN65HVD230 的 GND、电机电源的 GND、M5Stamp 的 GND，
最终要连到同一个参考地。分属不同电源时尤其重要。

## 三、编译与烧录步骤

三个工程互相独立，每个都是一个**独立的 CMake 工程**（构建体系已从 PlatformIO 迁到 CMake，
详见 [CMake 构建说明](CMake构建说明.md)）。

用 VS Code 打开对应文件夹 → 状态栏选预设 → Build；烧录用
**Terminal → Run Task → cmake: flash**。

| 工程 | 预设名 | 构建目录 |
|---|---|---|
| `firmware/esp32_master` | `esp32-master` | `<工程>/build` |
| `firmware/esp32_bridge` | `esp32-bridge` | `<工程>/build` |
| `firmware/stm32_f103` | `stm32-f103` | `C:/cmake_build/target-vehicle/stm32` |

> ★ STM32 的构建目录**故意**放在纯 ASCII 路径下：Windows 上的 GNU binutils
> （具体是 `arm-none-eabi-objcopy`，负责把 ELF 转成 `.bin/.hex`）不认 UTF-8 路径，
> 路径里的中文会让它找不到文件。ESP32 不受影响，因为镜像由 `esptool.py`（Python）生成。
> 原因与定位过程见 `firmware/stm32_f103/CMakeLists.txt` 顶部。

命令行等价（任何一块板都是这三步）：

```bash
cmake --preset <预设名>                          # 配置
cmake --build --preset <预设名>                  # 编译
cmake --build --preset <预设名> --target flash   # 烧录
```

### 3.1 ESP32 主机（发射端）

```bash
cd firmware/esp32_master
cmake --preset esp32-master
cmake --build --preset esp32-master
cmake --build --preset esp32-master --target flash     # 串口: $env:ESP32_PORT="COM5"
cmake --build --preset esp32-master --target monitor   # 460800 波特率
```

烧完打开串口，会打印：

```
[ESP-NOW] 就绪, 信道=6, 本机MAC=XX:XX:XX:XX:XX:XX
========= 靶车 ESP32 主机控制台 =========
```

**记下打印出来的本机 MAC**，后面填到桥接端可以改成定向发送（可选，但能抗干扰）。

### 3.2 M5Stamp S3 桥接端

```bash
cd firmware/esp32_bridge
cmake --preset esp32-bridge
cmake --build --preset esp32-bridge
cmake --build --preset esp32-bridge --target flash     # 串口: $env:ESP32_PORT="COM5"
cmake --build --preset esp32-bridge --target monitor   # 115200 波特率
```

正常启动会打印：

```
==============================================
  靶车 · M5Stamp S3 桥接端
  ESP-NOW -> UART -> STM32 -> CAN -> DM-G6220
==============================================
[ESP-NOW] 就绪 信道=6 本机MAC=XX:XX:XX:XX:XX:XX
[UART] Serial1 TX=G1 RX=G2 921600 bps
```

> M5Stamp-S3Bat DIP 进入下载模式：**长按 PWR 键约 3 秒**，等待烧录。
> 单击 PWR 开机/复位，双击关机。

### 3.3 STM32F103C8T6

```bash
cd firmware/stm32_f103
cmake --preset stm32-f103          # 构建目录在 C:/cmake_build/target-vehicle/stm32
cmake --build --preset stm32-f103
cmake --build --preset stm32-f103 --target flash     # OpenOCD + ST-Link
```

默认用 **OpenOCD + ST-Link** 烧录。换下载器改

| 下载器 | interface 配置 |
|---|---|
| ST-Link | `interface/stlink.cfg`（当前默认，还支持在线调试） |
| DAPLink | `interface/cmsis-dap.cfg` |
| J-Link | `interface/jlink.cfg`（需另装 J-Link 驱动） |
| 串口 ISP | 用构建目录里的 `firmware.hex` + 任意 ISP 工具（需 BOOT0 拉高再上电） |

## 四、分步验证（照这个顺序，出问题好定位）

> ★ 原则：**一次只验证一段链路**。四段一起上，出问题根本不知道是哪一段。

### 第 0 步：不接硬件的协议自测

```bash
powershell -ExecutionPolicy Bypass -File tools\run_protocol_test.ps1   # C 端
python tools\pc_monitor.py --selftest                                  # Python 端对拍
```

两个都要全绿。这一步验证的是"三端用的帧格式和 CRC 完全一致"，
如果这里就红，后面全白搭。

### 第 1 步：先验证 ESP-NOW（不接 STM32、不接电机）

1. 只给主机和桥接上电。
2. 看桥接端串口：应该每 500ms 打印一行

```
[桥接] 在线 rssi=-45 | 主机 ok=452 bad=0 dup=0 | 还没有 STM32 反馈 (检查 PA9/PA10 接线)
```

- `在线` 说明 ESP-NOW 通了；
- `bad=0` 说明 CRC 全对；
- 如果一直是 `【失联】`，检查：两颗板子信道是否都是 6、主机是否已在发、距离是否太远、天线是否接好。
- 如果 `bad` 一直在涨，说明有干扰或信道不一致。

### 第 2 步：验证 STM32 串口链路（不接电机）

接好 PA9/PA10/GND 后，桥接端应该变成：

```
[桥接] 在线 rssi=-45 | 主机 ok=452 bad=0 dup=0 | STM32 yaw=0.00 pitch=0.00 T=0C err=0 | 转发=452
```

出现 `STM32 yaw=...` 就说明 **STM32 收到命令并回传了反馈帧**，串口链路双向都通。

- 仍然显示"还没有 STM32 反馈" → 检查 PA9↔G2、PA10↔G1 是否交叉接对、**是否共地**、STM32 是否已烧录。
- `yaw` 一直是 0 而 `T=0` → STM32 通了但没收到 CAN 反馈，进入第 3 步。

### 第 3 步：验证 CAN 与电机（先悬空电机或空载）

1. 接好 CANH/CANL 和终端电阻。
2. 主机串口敲 `0`（定点模式，目标 0 度），再敲 `s` 看状态。
3. 桥接端日志里 `yaw` 开始跟随目标 → CAN 通了，电机在动。
4. 若 `yaw` 恒为 0、`err=0`、`T=0`：
   - 电机没上电 / 没使能；
   - CANH-CANL 接反；
   - **终端电阻缺失**（1 Mbps 下最常见）；
   - 波特率不对 —— 见下面「CAN 波特率推导」。

### 第 4 步：验证云台运动

主机串口敲：

| 命令 | 效果 |
|---|---|
| `1` | 正弦摆动（默认 ±30°，周期 6 秒）—— 最像做靶 |
| `2` | 三角扫描（±60°，20°/s，端点停 0.5 秒）—— 扫场 |
| `3` | 圆周（±20°） |
| `4` | 8 字（偏航 ±40°，俯仰 ±15°） |
| `0` | 定点保持 |
| `5` | 手动（配合 `y <角度>`）|

现场调参：

```
a 45        正弦幅度改 45 度
t 10        正弦周期改 10 秒
v 30        扫描角速度改 30 度/秒
k 80        MIT 位置增益 kp 改 80（跟不动就加，啸叫就减）
d 2         MIT 阻尼 kd 改 2（过冲就加）
y 30        手动模式转 30 度
x           急停（持续下发 ESTOP）
R           解除急停
```

### 第 5 步：验证安全机制（**别跳过这一步**）

| 测试 | 做法 | 期望现象 |
|---|---|---|
| 无线失联 | 给主机断电 | 300ms 内桥接打印"主机失联"，电机立刻松掉（能用手转动） |
| 串口失联 | 拔掉 G1/G2 任一根 | STM32 自己 300ms 超时，同样松掉电机 |
| 急停 | 主机敲 `x` | 电机立刻松掉，桥接日志显示 ESTOP |
| 恢复 | 主机敲 `R` | 500ms 斜坡内平滑恢复使能，不冲击 |
| 电机自报错 | 堵转电机 | `err` 变成非 0，桥接显示 FAULT；敲 `e` 清错后恢复 |

## 五、CAN 波特率推导（1 Mbps，必须精确）

STM32F103 的 bxCAN 挂在 APB1 上，APB1 = 36 MHz。

```
预分频 = 2          → tq = 1 / (36MHz / 2) = 55.556 ns
位时间 = 1(SYNC) + (TS1+1) + (TS2+1)
要 1.000 Mbps → 位时间 = 1.000 us → 1000 ns / 55.556 ns = 18 tq
1 + (TS1+1) + (TS2+1) = 18  →  TS1 = 15, TS2 = 2
```

**★ 这里有个真实的坑，记下来避免重踩：**
达妙官方例程是 STM32**F4** 的，用的是 `BS1 = 15TQ / BS2 = 5TQ`。
但 F4 的 APB1 = 42 MHz，F103 是 36 MHz。照搬到 F103 会得到
`21 tq × 55.556 ns = 1.1667 us ≈ 857 kbps`，**总线直接不通**，
而且现象是"完全没有反馈"，很容易误判成接线问题。

本工程的正确值在 `firmware/stm32_f103/include/config.h`：

```c
#define CAN_BTR_BRP_VAL   1u    /* 预分频 2 */
#define CAN_BTR_TS1_VAL   15u   /* 16 tq */
#define CAN_BTR_TS2_VAL   2u    /* 3 tq  */
#define CAN_BTR_SJW_VAL   0u    /* 1 tq  */
```

## 六、达妙 DM-G6220 CAN 协议速查

CAN ID 规则（电机 ID = 1）：

| 功能 | CAN ID | 数据 |
|---|---|---|
| MIT 控制 | `0x000 + id` = 0x001 | 见下方字节布局 |
| 位置速度模式 | `0x100 + id` = 0x101 | float pos + float vel |
| 速度模式 | `0x200 + id` = 0x201 | float vel |
| 位置速度电流 | `0x300 + id` = 0x301 | float pos + u16 vel + u16 cur |
| 使能 | `id + 模式ID` | `FF FF FF FF FF FF FF FC` |
| 失能 | `id + 模式ID` | `FF FF FF FF FF FF FF FD` |
| 保存零点 | `id + 模式ID` | `FF FF FF FF FF FF FF FE` |
| 清除错误 | `id + 模式ID` | `FF FF FF FF FF FF FF FB` |

MIT 控制帧字节布局（`dm_motor.c` 里逐位实现）：

```
data[0] = pos_tmp >> 8
data[1] = pos_tmp & 0xFF
data[2] = vel_tmp >> 4
data[3] = ((vel_tmp & 0xF) << 4) | (kp_tmp >> 8)
data[4] = kp_tmp & 0xFF
data[5] = kd_tmp >> 4
data[6] = ((kd_tmp & 0xF) << 4) | (tor_tmp >> 8)
data[7] = tor_tmp & 0xFF
```

量程（**必须与电机固件里的配置一致**，改过就要同步改 `config.h`）：

| 参数 | 值 | 位数 |
|---|---|---|
| 位置 PMAX | ±12.5 rad | 16 bit |
| 速度 VMAX | ±45 rad/s | 12 bit |
| 力矩 TMAX | ±10 Nm | 12 bit |
| Kp | 0 ~ 500 | 12 bit |
| Kd | 0 ~ 5 | 12 bit |

反馈帧（电机 → 主控）：

```
data[0] = (错误码 << 4) | 电机ID
data[1..2] = 位置(16bit)   data[3..4高4位] = 速度(12bit)
data[4低4位..5] = 力矩(12bit)   data[6] = MOS温度   data[7] = 线圈温度
```

## 七、常见问题速查

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 桥接一直打印"失联" | 信道不一致 / 主机没发 / 天线没接 | 两端 `ESPNOW_CHANNEL` 都改成 6；看主机串口 `TX ok` 是否在涨 |
| `bad` 计数持续增长 | 无线干扰、信道被占 | 换信道（两端一起改）；改成定向发送（填对端 MAC） |
| 桥接显示"还没有 STM32 反馈" | TX/RX 没交叉、没共地、STM32 没跑 | 检查 G1→PA10、G2←PA9；量 GND 是否连通 |
| 有反馈但 `yaw` 恒为 0、`T=0` | CAN 不通 | 终端电阻、CANH/CANL 接反、电机没上电、波特率 |
| 电机通电后立刻松开 | 看门狗超时（没收到有效命令） | 看桥接是否在正常转发；主机是否在发 |
| 电机啸叫/高频抖动 | kp 太大或 kd 太小 | `k 40`、`d 2` 逐步调 |
| 电机跟不上/滞后明显 | kp 太小 | `k 100` 逐步加，配合 `d` |
| 角度整体偏移或放缩不对 | 电机实际量程 ≠ `config.h` 的 PMAX/VMAX/TMAX | 用达妙 DMTool 读电机实际配置并同步 |
| 电机方向反了 | 机械安装方向 | 主机端用 `y` 手动给 +30 看实际转向；需要反向就在 `apply_command()` 里对 `yaw_deg` 取负 |
| 上电瞬间云台猛甩一下 | 上电位置离零点太远 | 先手动把云台摆到接近 0 度再上电；增益斜坡已经是 500ms，不要改太小 |
| CMake 编 STM32 报 `arm-none-eabi-objcopy.exe: ...: No such file or directory`（路径里是乱码） | **构建目录路径含中文** —— Windows 的 GNU binutils 不认 UTF-8 路径（链接其实成功了，卡在 ELF→bin 的 objcopy） | `CMakePresets.json` 里 `stm32-f103` 的 `binaryDir` 已指向纯 ASCII 的 `C:/cmake_build/target-vehicle/stm32`；若你手工改过位置，改回 ASCII 路径即可 |
| CMake 报 `no CMAKE_C_COMPILER could be found` / 编出宿主机程序 | 没走预设，缺 `-DCMAKE_TOOLCHAIN_FILE` | `cmake --preset <预设名>`，不要 `cmake -S . -B build` 裸跑 |
| 报 `找不到 PlatformIO 的 packages 目录` | 这台机器没装过 PlatformIO，或路径不在默认位置 | 装一次 PlatformIO，或 `-DPIO_PACKAGES_DIR=<路径>/packages` |
