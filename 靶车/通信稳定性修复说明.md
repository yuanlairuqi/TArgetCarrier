## 证据与原因分类

以下为确定存在的代码或构建配置缺陷，但它们在用户实机上各占多少故障比例仍未验证：

1. GEEK 主循环用 `vTaskDelay(pdMS_TO_TICKS(5))`；实际构建 `CONFIG_FREERTOS_HZ=100`，宏整数运算结果为 0。`vTaskDelay(0)` 不进入阻塞，可能挤占同核低优先级 LCD/idle，并触发监控 idle 的任务看门狗告警。现在至少阻塞 1 tick；未改系统节拍，未声称已证实发生过看门狗复位。
2. GEEK 实际 sdkconfig 默认启用 `CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG`，和 GU/1 使用同一个原生 USB 接口。原 README 虽声明日志走 UART0，构建配置却仍可能把文本写入二进制通道。现在 defaults 显式禁用 secondary USB console，最终 sdkconfig 已核对为 SECONDARY_NONE。普通 UART0 日志保留。
3. 无线接收仅一个 8 槽 FIFO，波形与控制状态共用；满队列只能丢包，且未计数。现在控制 RX 8、波形 RX 16、硬 STOP 保留槽 1，控制/STOP 优先，丢包与峰值可见。故障注入 500 个波形包不会占用控制槽。
4. `sending` 只等 MAC 回调解除，没有超时；回调不来会永久停发。现在 250ms 触发清队列、撤销会话、注销/反初始化 ESP-NOW，至少等待 1000ms 后重建加密 peer/回调；不靠直接清 busy 启动第二个并发发送。恢复操作每次有界，失败后按 1s 间隔再尝试，不阻塞控制任务、不重放运动。
5. 上位机原来没有 USB 自动重连；无线状态停滞也没有独立废止 USB 传输会话。现在区分 USB / 无线状态 / STM32，失效后清 held、待发启动/调速/方向和待确认运动，改变 generation/session，重新 QUERY→STOP→真实 STM32 确认。USB 自动重开最多 8 次，退避 0.5/1/2/4s（后续封顶 4s），手动断开或取消会终止重连。
6. 从机 `bridge_receive`、发送失败处理曾在业务锁外写 bridge，BLE 状态回调在锁内读同一对象，存在共享资源竞争。现在用同一 mutex 保护；UART 每次读取预算从 96 增至 256 字节，发送前检查 TX 环形缓冲可用空间，避免在控制路径等待满 TX 缓冲。

保留的运行日志：`runtime-log-evidence/connection-0.log`、`connection-1.log`。3.0 日志中 328 次 `0x99`、366 次 `0xB9` 是**状态转换记录**，不能当丢包统计；两种 flags 都含 STM 在线位 `0x08`，差异为当前命令 APPLIED `0x20`。处理新事务时临时未确认是正常情况。该日志还出现一次 STM 离线转换、一次“运动确认超时”通知、8 条 error=7 的转换记录。日志缺少 RF/复位数据，也不能证明这些会话都使用了 GEEK 链路，不能把全部现象归因为无线断联。日志副本和解析 JSON 随报告保存。

可疑但未验证的实机因素：电机供电压降、地弹、驱动干扰、天线/屏蔽/距离、USB 供电与接触、2.4GHz 干扰、BLE/Wi-Fi 共存实际抢占、实际信道和配对参数、设备固件版本不一致。没有电源示波记录、RF 抓包或两端启动日志，不能排除这些因素。

## 消息、吞吐和参数

框架不变：Vue → GU/1 USB → GEEK → 加密 ESP-NOW WN/1 → 从机 → UART v2 → STM32。WN 主体 64B + HMAC 16B = 80B；USB 每帧 72B；UART 每帧 32B、115200/8N1，即理论有效上限 11520B/s。USB API 的 115200 设置不是原生 USB 实际吞吐上限；RF 可用吞吐受干扰与调度影响，未实测。

| 参数 | 当前值与依据 |
| --- | --- |
| PC 运动心跳 | 保留 200ms，每次新序号；未获确认不会无限排队 |
| PC 待机保活 | 保留 400ms 新 STOP，需真实 STM32 确认 |
| 从机周期状态 | 保留 200ms；命令接收结果与 UART 输出确认分开 |
| 波形间隔 | `NOW_WAVE_GAP_MS=20`，最多 50 帧/s；控制可立即绕过波形令牌，不等待波形窗口 |
| 波形负载 | 最多约 4000B/s 无线应用数据、3600B/s USB 帧数据；不是 RF 总空口开销。常规 5 命令/s + 5 周期状态/s 再加约 800B/s 无线状态；总量不是原生 USB/115200 UART 饱和的证据 |
| 采样窗口/容量 | 保留 100ms 窗口、512 边沿、20B 原始采样分包。最多 173 个包，50 帧/s 理想传输约 3.46s；原 5s 整段期限保留，不能无限追传旧采样 |
| 波形 TX | 单槽背压，未入队时保留当前片等待后续 tick；RX 波形满则丢弃，整段序号/CRC 不全就不绘图，下一段恢复 |
| 队列期限 | 控制/波形 RX 与普通 TX 保留 100ms；旧硬STOP RX仍交协议层作停机，但不续租/不重新授权；GEEK USB 队列新增 100ms 过期丢弃，部分 USB 帧 250ms 无进展即废止传输。硬 STOP TX 可例外，但已失效 session 不能解锁 |
| MAC 回调保护 | `NOW_RADIO_CALLBACK_MS=250`；不延长原应用 ACK 超时，失败撤销会话 |
| 无线驱动恢复间隔 | `NOW_RADIO_RECOVERY_MS=1000`，不重启 MCU，不删除配对参数，不自动跳信道 |
| GEEK/PC 无线判失效 | 600ms，大于 200ms 状态周期，容纳短暂缺包；波形不能续这个状态租约 |
| USB 数据超时 | PC 2.5s 无有效 GU 帧才重开 USB，能与“USB活着但无线不回包”区别 |
| UART | 保留 ACK 400ms、重发 100ms、在线 600ms；同 token 重发用于 UART 确认，STM32 防重并且重复运动不续租 |
| 下游保护 | 保留 S3 800ms 命令租约、STM32 500ms 运动租约；PING 不续运动租约 |

上述保护时间不是机械停车距离或硬实时停止上限。250ms 是异常检测策略，实机可通过回调超时计数判断是否过紧；不能只调大 ACK/租约来掩盖拥塞。原生 FreeRTOS/Wi-Fi 回调只复制到有界队列/更新原子计数，HMAC/CRC、业务和诊断在普通任务处理。STM32 1ms 服务、硬停止与租约实现仅关联检查和模型回归，未修改。

Wi-Fi 初始化仍固定 STA、配置 peer/channel、`WIFI_PS_NONE`，没有新增 AP 关联、扫描或跳频。最终从机构建保留 `CONFIG_SW_COEXIST_ENABLE=y`。诊断同时返回配置/实际信道；重建只重新初始化 ESP-NOW 和加密 peer，不重新初始化 BLE/Wi-Fi。80B 报文小于 ESP-NOW v1 250B 上限。

## 失效与恢复的执行路径

- UI 心跳丢失、人工急停、USB/无线失效：PC 清 held/待发命令，创建新 STOP 屏障，旧写任务即使等待锁结束也会因 generation 或 100ms 期限失效；断线前已排入 owner 回调的 move 同样失效。
- GEEK 在**读取缓存前**检查 USB/PC/无线租约，清发送队列和 USB 缓存，使用旧会话只尽力发一次硬 STOP，阻止该会话恢复；没有新 QUERY、新 session、新 STOP 确认就不放行运动。重复/回退运动 seq 被拒绝。
- 从机在命令处理前执行 robot/无线租约检查。无线驱动异常换代调用 `now_control_link_lost` 增加 epoch、撤销无线控制、生成 STOP revision。原 bridge 把 STOP 抢占进 UART；如果 UART 不通，STM32 自身租约失效路径继续有效，界面显示未知/待确认。
- 从机/总机复位、epoch 变化：PC 更新挑战值、随机 session、重新握手；已淘汰的 boot/epoch 不能被迟到状态回滚。MAC 成功只记 MAC 成功；没有假造从机或 STM32 ACK。
- 重连后只有 STOP/QUERY 保活，不保存旧运行配方为自动启动动作。用户必须再次点击启动。旧波形标记历史，停止确认未通过不显示“已停止”。

## 诊断字段

PC“连接诊断”显示 USB/无线/STM32 状态、状态年龄、控制确认延迟、两端 RX 峰值/丢包、MAC 回调超时/驱动重建、复位原因 SDK 编号、最大循环间隔、USB 丢弃、配置/实际信道。固件 `link_diag` 最多每 5s 一条；USB 总机 INFO 每 1s、从机 STATUS 200ms，复用既有频率。文件日志沿用轮转限制。部分固件诊断计数通过低 8/16 位发送，长时间测试应注意回绕。

GU INFO 扩展版本在 body[63]=1：44..47 u32 总机 boot，48 复位原因，49 实际信道，50/51 RX/TX峰值，52..53 RX丢包，54..55 回调超时，56..57 重建次数，58..59 循环最大间隔ms，60..61 USB丢弃，62 HMAC失败低8位。
WN STATUS 扩展 body[27]=1：28 复位原因，29/30 RX/TX峰值，31 波形RX丢弃低8位，32..33 控制RX丢包，34..35 回调超时，36..37 重建次数，38..39 循环最大间隔ms；40..59 业务状态不变，CRC/HMAC仍覆盖扩展。完整认证失败计数也记 UART0 的限频诊断日志。旧协议读者忽略这些附加诊断；COMMAND 保留字段校验不放宽。

## 获准烧录后的复现与验收步骤（本轮未执行）

1. 保留当前可用固件和日志，核对真实板型、MAC、信道、node、同一套私密配对；按原流程配对并重新编译，再另行烧录。先隔离电机驱动信号，不使机械运动。
2. 新上位机连接后观察 USB/无线/STM 三段；没有 STOP 双端确认时必须不能启动。配置/实际信道一致，记录两端 boot/reset reason。只接 USB 能看到总机 INFO，但不得因此显示从机或 STM 在线。
3. 无波形、持续波形、波形+快速调参分别至少运行 10 分钟；记录 ACK 延迟最大值、循环间隔、队列峰值/丢包、回调超时/复位。允许波形明确缺段/丢弃，不能假画完整波形；控制队列不得无限增长、STOP不能等整段波形发完。
4. 分别拔 USB、屏蔽/关闭从机无线、复位总机、复位从机、断开 STM UART；核对只有对应链路判失效，不把 MAC成功当执行成功。无法确认停脉冲时，UI必须未知/待确认。
5. 每种故障至少恢复 20 次，故障前持续发送启动/调速/换向；恢复后先观察 30 秒不点启动，确认无输出、无旧事务执行、停止屏障重新建立。之后只在用户明确点击新启动时才允许输出。USB重连次数耗尽时提示手动重连，人工断开不会自己重开。
6. 通信和停止验证通过后，另外安排低速空载电机验收。对电机加速/减速、换向和波形同时传输，记录3.3V供电、复位脚、UART与PUL/DIR波形，排查压降/干扰；对停机距离、驱动禁能、机械限位单独验收。软件结果不能替代这些测量。
