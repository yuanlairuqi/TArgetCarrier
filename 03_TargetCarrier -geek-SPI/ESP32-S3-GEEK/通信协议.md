# USB 与 ESP-NOW 协议

工程：ESP32-S3-GEEK_无线遥控总机。仅控制一个已配置目标，设备 ID 接口保留；没有广播运动、自动配对或扫描并控制全部设备的逻辑。

## 物理接口与框架

本机使用已安装 ESP-IDF 6.1、Xtensa GCC 15.2.0、FreeRTOS。依据本地官方 ESP32-S3-GEEK V1.1 原理图，USB-A D-/D+ 经电阻连接 ESP32-S3 GPIO19/20；使用芯片 USB Serial/JTAG 控制器的 CDC 串口端点，电脑端 pyserial 打开枚举的 COM 口。设置 115200/8N1 是串口 API 参数，USB 实际速率由 USB 控制器决定。日志走 UART0，避免混入二进制 USB 数据。没有添加 USB-UART 桥芯片，也没有使用 GEEK 外露 UART 代替 USB。

GEEK 是 240×135 ST7789 LCD，不是 OLED；复用已有 SPI 驱动（MOSI11、SCLK12、CS10、DC8、RST9、BL7），低优先级独立任务显示 USB、从机状态接收、目标 ID、信道、指令速度和 STM 输出确认。LCD 实物显示仍待验证。从机原有 OLED、UART、BLE、采样代码保留；OLED 控制来源显示修正为实际 BLE/无线所有者。

## USB GU/1

所有数字为小端。每帧固定72字节，输入采用有界滑动解析，允许拆包、粘包及噪声后重新同步。

| 偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0 | 2 | ASCII GU |
| 2 | 1 | USB版本1 |
| 3 | 1 | 类型：1电脑请求；2从机状态；4波形；5总机信息 |
| 4 | 64 | 主体；1/2/4为完整WN主体，5为信息块 |
| 68 | 4 | CRC32/IEEE，覆盖0..67 |

电脑请求仅允许有效 WN QUERY/COMMAND、固定 node。总机信息块：0=无线配对就绪，1=信道；4=u32 node，8=u32总机 uptime_ms，12..17=STA MAC；20/24/28/32/36/40分别为u32无线提交、MAC成功、MAC失败、提交失败、排队过期、控制队列丢旧包计数。扩展字段见末节。信息块不代表从机在线。

## 无线 WN/1

沿用原版64字节主体 +16字节 HMAC-SHA256 截断标签，共80字节；同时启用 ESP-NOW 加密单播 PMK/LMK，固定 STA peer 与同一2.4GHz信道。HMAC使用独立32字节AUTH_KEY。接收检查目的MAC、本地MAC、来源MAC、长度、HMAC、魔数/版本及CRC。密钥不通过USB发送。没有自动明文降级。

| WN主体偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0 | 2 | WN |
| 2 | 1 | 版本1 |
| 3 | 1 | 1 QUERY；2 COMMAND；3 STATUS；4 GPIO采样扩展 |
| 4 | 4 | node ID，范围1..65535 |
| 8 | 4 | 从机 boot 随机挑战值 |
| 12 | 4 | 从机 epoch，控制权变更/失联后递增 |
| 16 | 4 | 电脑非零随机 session |
| 20 | 4 | COMMAND序号；STATUS请求序号/当前已接收序号 |
| 24..59 | 36 | 各类型字段，见下 |
| 60 | 4 | CRC32/IEEE，覆盖0..59 |

QUERY只设置node，其余8..59清零。COMMAND的24..39是原16字节v3指令；40..59清零。原指令：版本3、方向0/1/2、速度0..100%、模式0持续/1交替、u32 seq、u32正转毫秒、u32反转毫秒；运动速度1..100%，STOP速度0且模式/时间归零，交替每段100..3600000ms。原STM32 UART v2、换向死区与速度映射未改动，不在GEEK生成PWM。

STATUS：24=result；25=owner（0无、1 BLE、2无线）；26=响应的请求类型；40..59=原20字节状态。result：0接受、1 BLE占用、2挑战变化、3需要STOP、4会话不符、5重复/旧序号、6命令错误、7过期。旧版字段中“connected”表示逻辑控制连接，在无线模式不能解释为BLE实连。

四层证据必须分开：

1. esp_now_send返回OK只表示提交；MAC回调成功只表示链路层交付。
2. 带正确 boot/epoch/session 的 STATUS result=0 才说明从机应用接收该请求。
3. STM32确认必须同时匹配ESP/STM序号、当前bridge revision、completed_phone、online、confirmed、非waiting及APPLIED，再由电脑校验方向/速度/模式等字段。
4. APPLIED只说明STM固件报告输出已应用；GPIO采样也不是编码器位置、驱动器到位或实际电机运动证明。

## 会话、停止与超时

电脑先QUERY取得boot/epoch，再用新session发STOP。实际STM停止确认之前不能运动。BLE连接占用控制权，连接/断开撤销旧无线session。重复/旧序号不会重新启动或续租；旧STOP仍执行停止。电脑对运动不做报文重试，沿用现有每200ms新序号指令刷新租约；同参数不会重启STM交替周期。STOP确认超时仅重试STOP，用新事务序号及新的确认时钟。

从机800ms无新鲜命令/链路异常撤销session并停机；100ms以上RX排队包拒绝。从机原STM UART链路还有自身超时与停止流程。总机USB600ms无请求或USB断连，尽力发送一次STOP并锁定转发，等待新QUERY；STOP失败时从机租约仍负责停止。重新连线/恢复不会自动恢复旧运动。

无线发送队列：控制4帧，波形1帧；单次仅一个SDK发送等待回调，控制优先；STOP清空待发运动/波形。过期100ms的非STOP待发包丢弃；SDK发送失败不自动重放运动；控制队列满丢最旧状态/请求并计数，安全性依赖序号、租约和电脑确认超时。发送回调不执行控制/USB/UART。

USB RX环256字节，单tick最多读144字节；TX环256字节；应用状态队列8帧、波形16帧，非阻塞写，保留一个未写完帧后优先状态；队列满丢旧包。波形丢包会使该段校验失败，不能以插值伪造完整采样。LCD任务不持有控制锁传SPI。

## GPIO波形扩展

WN kind4保留节点/boot/epoch/session。24=u32从机采集开始uptime_ms；28=u16分包index；30=u16总包数；32=来源1（从机MCPWM GPIO采样）；40..59为原20字节pulse_wire包。20..23、33..39保留零。起始时间是从机单调时钟，约49.7天回绕，与电脑时钟没有同步；电脑另记接收墙钟。

原波形头保留id、flags、初始电平、硬件计数频率hz、窗口ticks、边沿数、PUL/DIR引脚、来源版本；数据包每包最多3个(tick:u32,tag:u8)；尾包保留包数/边沿数与全段CRC。100ms采样窗口，最多512边沿；正常最大173包。按低优先级有背压发送，5秒内未完成放弃，段间有间隙，不保证连续采集。高频溢出/边沿丢失必须标记，不绘成可信波形。

电脑同时检查会话、来源、起始时间、总数、分包顺序、5秒超时，再执行原pulse_wire顺序/CRC/边沿连续性校验；丢包/重复/乱序放弃整段，等下一头包恢复。保留冻结/断线历史标识及CSV来源信息。


## 2026-10-23 通信诊断扩展

GU/1、WN/1主体尺寸及业务状态不变。INFO body[63]=1 时，44..47=总机boot，48=复位原因，49=实际信道，50/51=RX/TX峰值，52..53=控制RX丢包，54..55=MAC回调超时，56..57=无线重建，58..59=循环最大间隔ms，60..61=USB丢弃，62=HMAC失败低8位；16位数字均小端。

STATUS body[27]=1时，28=复位原因，29/30=RX/TX峰值，31=波形RX丢弃低8位，32..33=控制RX丢包，34..35=回调超时，36..37=无线重建，38..39=循环最大间隔ms。CRC/HMAC继续覆盖整个主体，旧读者可忽略诊断。COMMAND校验不放宽。完整说明见工程根目录《通信稳定性修复说明.md》。
